# Специфікація бізнес-процесу «Оплата, фіскалізація та закриття чека» (`UC-10`)

## 1. Намір, межі та обрана форма
**Мета:** описати єдиний наскрізний процес оплати чека (`UC-10 Оплатити` із Завдання 2, сценарії `SC-10`–`SC-15` із Завдання 3) в одній декларативній нотації. Прийом і приготування замовлень (`UC-01`–`UC-08`) залишаються поза обсягом (out of scope).

**Обрана форма:** **Activity-діаграма (`Mermaid flowchart TD`)**. Обрана замість `stateDiagram-v2` (бракує доріжок ролей для координації акторів і шлюзів) та `BPMN 2.0 XML`.

## 2. Ролі та кроки процесу
* **Учасники:** `Гість / Офіціант`, `Expirenza`, `Ресторанна система`, `ПРРО`.
* **Послідовність:**
  1. **Вибір каналу оплати:** `Гість` ініціює QR-оплату через `Expirenza` або `Офіціант` підтверджує оплату готівкою чи терміналом.
  2. **Перевірка результату `Expirenza`:** при підтвердженні, система переходить до фіскалізації; при відмові (`FAILED`) або таймауті — залишає чек відкритим і надсилає помилку.
  3. **Фіскалізація в `ПРРО`:** при отриманні фіскального номера система закриває чек при помилці або таймауті — залишає чек відкритим і сповіщає офіціанта.

  4. **Паралельний блок (`fork` / `join`):** після закриття чека одночасно виконується інформування офіціанта та перевірка відкритих чеків столу, якщо їх нема то стіл отримує статус вільний.

## 3. Повідомлення процесу та реакція на відсутність відповіді

| Повідомлення                                                | Відправник → Отримувач                      | Дія при отриманні відповіді                                         | Дія без відповіді (таймаут)                                    |
| :---------------------------------------------------------- | :------------------------------------------ | :------------------------------------------------------------------ | :------------------------------------------------------------- |
| `payByQr(checkId, amount)`                                  | `Гість` → `Expirenza`                       | Шлюз обробляє платіж і формує webhook                               | Оплата не стартує, чек лишається відкритим                     |
| `sendPaymentWebhook(checkId, status)`                       | `Expirenza` → `Ресторанна система`          | `PAID`: фіскалізація в `ПРРО`; `FAILED`: помилка гостю              | Система фіксує таймаут, лишає чек відкритим і надсилає помилку |
| `confirmPayment(checkId, method)`                           | `Офіціант` → `Ресторанна система`           | Зчитування даних `CHECK` і запит до `ПРРО`                          | Запит не доходить до системи, оплата не ініціюється            |
| `registerReceipt(checkId, total_amount, method)`            | `Ресторанна система` → `ПРРО`               | `fiscal_number`: закриття чека; `fiscalError`: сповіщення офіціанта | Чек лишається відкритим, офіціант отримує `notifyWaiter`       |
| `notifyWaiter` / `showPaymentResult` / `printFiscalReceipt` | `Ресторанна система` → `Офіціант` / `Гість` | Асинхронне інформування (відповідь не очікується)                   | Процес завершується без очікування відповіді                   |

## 4. Критерії прийняття
* Діаграма містить єдиний старт, кінцеві стани для всіх гілок (без «глухих кутів» і недосяжних вузлів), розгалуження та паралельний блок.
* Для кожного повідомлення визначено відправника, отримувача та поведінку процесу при відсутності відповіді.
* Усі назви повідомлень та атрибути збігаються і трасуються до вимог `REQ-13`–`REQ-18`.
